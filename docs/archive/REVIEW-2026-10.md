# Spec Review: Requirements & Architecture

**Reviewed:** every file in this repo, as of commit `4e3f514`.
**Date:** 2026-10-11
**Companion:** [`demo/walkthrough.html`](demo/walkthrough.html) is a linear, clickable walkthrough of Phase 1 for stakeholders. It builds in the fixes recommended here, and each step has a sign-off checklist.

---

## 1. Bottom line

The spec covers a lot of ground, but it is not ready to build from. Three problems block an implementer:

1. **The answers in the Q&A files never reached the docs.** The `0x_*questions.md` files record decisions (Python/FastAPI, pure React Native, PostgreSQL only, local install, lock-based sync, guided tour, undo/redo and debug dashboards in Phase 1). Most downstream docs still describe the pre-decision options (Node *or* Python, Expo, WatermelonDB/IndexedDB, TimescaleDB + Redis + ClickHouse, Kubernetes, last-write-wins sync). An agent or engineer reading `requirements.md` or `system-architecture.md` builds the wrong system.
2. **There are two competing story sets with different IDs and priorities.** `user-stories.md` uses `AUTH-/ADMIN-/BCBA-/RBT-/COMMON-` IDs, and BCBA work is Phase 1. `user-stories/` + `traceability-matrix.md` use `US-xxx` IDs, and BCBA graphs/reports are P1 (Phase 2). Nothing maps one set to the other.
3. **The core offline + session-lock model has gaps that would lose clinical data.** These are covered in §4. They are the highest-risk part of the system, and the spec currently resolves them three different ways.

Before more spec writing, I recommend:

- Pick **one** source of truth per concern (one PRD, one story set, one architecture doc). Mark the rest as superseded or delete them.
- Get answers to the ~12 open decisions in §2. Most have a sensible default, which I've proposed.
- Adopt the sync/lock/data-integrity design in §4 as an ADR before any code exists.
- Have stakeholders walk the demo and sign off step by step. Every "Decision needed" callout in it maps to a row in §2.

## 2. Decisions needed from stakeholders

The ✅ default is what the demo shows. Each one is a recommendation, not an assumption I've already locked in.

| # | Question | Why it matters | ✅ Recommended default |
|---|---|---|---|
| D1 | **Does HIPAA or FERPA govern this data?** A school's student records are generally *education records* under FERPA, and HIPAA's Privacy Rule excludes them. If a separate clinical provider delivers the ABA services, HIPAA may apply instead or as well. | It changes consent, parent access rights, disclosure logging, and retention. It also decides whether "Parent" is a Phase 3 nice-to-have or a legal access right. | Have counsel confirm. Build to the stricter of the two: encryption, access audit, and FERPA-style parent access-on-request. |
| D2 | **What does a session lock cover?** The user's answer said "a session for a given student". The flows and mockups lock per *student + program*. | Per-program locks let two people run different programs on one student at once, which a 1:1 model doesn't need. They also multiply conflicts. | One lock per **student**. A session contains several programs. |
| D3 | **What happens to data recorded by a device after its lock was taken?** Today it is "moved to drafts", "discarded", or "server compares timestamps", depending on the doc. | These are real observations of a child. Silently dropping them is a data-integrity failure, and silently merging them can double-count. | Never drop it. The data is accepted and stored as **"recorded without lock"**, kept out of graphs until the BCBA accepts or rejects it, with both actions audited. |
| D4 | **Can a session start while offline?** No lock can be granted without the server. | RBTs in WiFi dead zones would otherwise be blocked from the core task. | Yes. The device takes a **provisional lock**. On reconnect it is confirmed, or, if someone else held the lock, the data goes into the D3 review queue. |
| D5 | **Offline authentication.** "Extend token lifetime locally" is not possible with JWTs, and the user's answer to Q10c ("browsing sensitive information") is incomplete. | It decides how long a lost phone exposes PHI, and whether a deactivated user can keep collecting data. | Unlock offline with a device PIN or biometric. The local store is encrypted. Allow at most **72h** offline, then require login. The server re-checks the account on sync; data from deactivated users is accepted but flagged. |
| D6 | **Local storage on the device.** The answer was "key-value". | Plain AsyncStorage is unencrypted. Storing PHI in it fails any encryption-at-rest requirement. | Encrypted SQLite (SQLCipher / op-sqlite), or encrypted MMKV for small data. The key lives in Keychain/Keystore. |
| D7 | **The 15-minute inactivity logout vs. a running duration timer.** | An RBT timing a 20-minute behavior episode would be logged out mid-measurement. | Timeouts pause while a session is active. The device locks to a PIN screen (data stays intact) rather than logging out. |
| D8 | **How is mastery evaluated?** "Custom" was answered, and the mockup says "can be any text". | Free text can't be evaluated, so "on track / mastered" alerts and trend flags can't be computed. | A structured rule: `metric ≥ X% for N of M consecutive sessions, with minimum trials per session`, plus a free-text note. Use a small rule set rather than a formula language. |
| D9 | **How is % correct calculated?** The testing doc contradicts itself on whether *Prompted* counts in the denominator (see §5). | Every graph, mastery check, and report depends on it. | % independent correct = correct ÷ (all trials except voided ones). Prompted counts as *not independent*. Make it a per-program setting. |
| D10 | **Environment banner colors.** There are three different schemes in the docs (§3). | The banner's whole purpose is to be unmistakable. | Demo = purple, Dev = green, QA = amber, **Prod = slim neutral bar** that still shows env, role, and time. A red Prod banner tells people in the real system that something is wrong. |
| D11 | **Is Demo a separate environment or a dataset you can install?** The Admin screen has "Install / Clear Demo Data" buttons. | Installing fake students into a database with 100 real ones mixes PHI and fake data, and a "Clear" button in Prod is a hazard. | Demo is its own **environment** with its own database. The install/reset buttons exist only when `ENV ∈ {demo, dev, qa}`, and the server refuses them in Prod. |
| D12 | **Session types.** The answer was "You decide". | It determines whether probes are special-cased, and whether a session can be billed later. | Phase 1 has `direct` and `probe`. `probe` hides prompt buttons and flags its data points. Observation and parent-training come later. |
| D13 | **Undo scope.** The user said "Forms". The docs also apply it to trials, events, and program edits. | Undo on clinical data after sync can't be a DELETE. | Forms use a client-side undo/redo stack. Data entry gets a separate **"void last"** action that appends a void event, so it works offline and after sync. |
| D14 | **Who may edit data after the fact, and is a reason required?** | Corrections to clinical data need an audit trail that explains them. | BCBA only in Phase 1. A reason is required. The original value is kept and the change shows in the session history. |

## 4. Architecture recommendations

### 4.1 Right-size Phase 1

The architecture diagram has an API gateway, five services, four workers, three databases, Redis, ClickHouse, SendGrid and Twilio. For 100 students on one local install, that is about ten times the needed moving parts, and each part is a place for an AI coding agent to stall.

**Phase 1 target:**

```
React Native app (RBT)  ──┐                         ┌── PostgreSQL 16 (single DB per environment)
                          ├── HTTPS ── FastAPI ─────┤
Next.js web (Admin, BCBA)─┘     (one process,       └── local disk: generated PDFs
                                 modules: auth, students, programs,
                                 sessions, sync, analytics, reports, admin)
Background work (report PDFs, trend flags): a jobs table in Postgres polled by one worker
process (`SELECT … FOR UPDATE SKIP LOCKED`). No Redis, no message broker.
```

Split services later, only when a measured need appears.

### 4.2 Store observations as an append-only log

Today trials, events and durations are mutable rows. Undo is `DELETE /trials/{id}`, sync does `UPDATE` by timestamp, and students cascade-delete everything. For clinical data that is synced from offline devices, invert this:

- **Every data point is an immutable event** with a **client-generated UUIDv7** as its primary key: `trial_recorded`, `event_recorded`, `duration_recorded`, `observation_voided`, `observation_corrected`.
- **Undo during a session** = append `observation_voided { target_id }`. It works offline, syncs cleanly, and leaves an audit trail without extra code.
- **Retroactive correction** = append `observation_corrected { target_id, new_value, reason }`.
- **Graphs and stats** are computed from the log (a view or a summary table that stays current), never stored as the source of truth.
- **Idempotent sync**: re-uploading the same event is a no-op (`ON CONFLICT (id) DO NOTHING`). This removes the need for `is_synced` and `offline_id` on server tables.
- `ON DELETE RESTRICT` everywhere under `students`. Discharge is a status, not a delete.

### 4.3 Session lock + offline sync (replaces ADR-001's conflict rules)

```
Lock = one row per student: {student_id, holder_user_id, holder_device_id, epoch, acquired_at, heartbeat_at}
```

| Situation | Behavior |
|---|---|
| Start, online | `POST /students/{id}/lock`. Granted if free or stale (heartbeat older than 15 min). If someone holds a live lock, the client shows the holder and a **Take over** confirm. A takeover increments `epoch`. |
| Start, offline | The device records a *provisional* lock with `epoch = null` and starts collecting. |
| During session | Every observation carries `{device_id, lock_epoch}`. Heartbeat every 60 s while online. Data is always written locally first, then pushed from an outbox. |
| Reconnect | Upload the outbox in order. The server stores **every** event. Events whose epoch matches the current lock (or a confirmed provisional lock) go live. All others get `review_state = 'pending'`. |
| Lock taken from you | Banner: "Ms. Rivera took over this session at 10:42. You can keep recording; your data will go to the BCBA for review." There's no reclaim ping-pong: taking the lock back uses the same takeover confirm. |
| BCBA review | A queue lists pending sessions side by side. **Accept** (counts in graphs) or **Reject** (kept, hidden, reason required). Both actions are audited. |

This keeps the user's rule ("priority to the last user holding the lock") for *what counts automatically*, without ever destroying an observation.

### 4.4 Data model corrections

The SQL in `data-models.md` won't run as written, and it is missing core entities.

- **Errors**
  - The `students_bcba_role` CHECK uses a subquery, which PostgreSQL doesn't allow. Use a trigger, or `bcba_assignments` with an FK plus a role check in app code.
  - `CREATE TABLE … PARTITION OF audit_logs` fails because the parent isn't declared `PARTITION BY`. The `id`-only PK is also invalid on a partitioned table, since it must include the partition key.
  - The example migration inserts `description` into `audit_logs`, which has no such column.
  - `idx_users_email` duplicates the UNIQUE index.
- **Missing entities**
  - `treatment_plans`: the confirmed hierarchy is Student → Plan → Program → Target, but programs hang directly off students.
  - `session_locks` and `devices`.
  - `staff_assignments` (with history) to replace `assigned_rbt_ids UUID[]`, which has no FK integrity and no history. FR-2.2 requires history.
  - `program_versions`: today, versioning by copying the program row breaks graph continuity. Use a stable program id plus a versions table, and have each observation reference the version that was active.
  - `phases`, where a phase change is a *point between sessions* tied to a session or timestamp, not a date. Several sessions per day make dates ambiguous.
  - `consents` (type, source, granted_by, date, revoked_at).
  - `refresh_tokens` (rotation and revocation), `tour_progress`, and `review_queue`.
- **Frequency rate needs an observation window per program.** The session's total duration is wrong when three programs share a session.
- **Phase 1 needs `audit_logs`.** The pilot uses real students in Phase 1, but full audit logging is scheduled for Phase 3.

### 4.5 Security details to fix now

- Web tokens: `screen-flows.md` puts both tokens in **localStorage**, which is exposed to any XSS. Use httpOnly + SameSite cookies for web, and Keychain/Keystore for mobile.
- The JWT payload embeds `assigned_students`. That list goes stale the moment a BCBA reassigns someone. Check assignments on the server per request.
- Debug dashboard "stack traces" and "exposed state for integration tests" must be **impossible in Prod**. Gate them on the server by `ENV`, not by hiding the UI.
- Photo uploads and student photos on cards are PHI on a phone screen in a classroom. Make them optional, default to initials, and show nothing on the lock screen.

### 4.6 Testability hooks that a coding agent can't fake

The answers asked for row counts so the system "is not cheating". Row counts alone are easy to fake or misread. Add:

1. **Write receipts:** every sync response returns the server row ids and a running per-session checksum (count + hash of event ids). The device shows "Server confirmed 37/37". This is the real "did it actually write?" check.
2. **Canary probe** on the health page: write a row, read it back on a separate connection, delete it, and report latency. Fails loudly.
3. **Row counts from `count(*)`** for the core tables, labelled with environment and DB name, plus a "rows changed in last 5 min" column so a tester can watch the effect of an action.
4. **Deterministic test clock and seed:** `X-Test-Now` header (non-prod only) and a fixed seed, so trend and mastery logic is reproducible.
5. **`data-testid` everywhere.** The mockups use `#id` selectors and the Playwright samples use text selectors (`button:has-text("✓ CORRECT")`). Pick `data-testid`, matching `requirements.md` FR-11.4.
6. **`/api/v1/_test/reset?fixture=…`** (non-prod only), so an agent can put the system into a known state in one call.

### 4.7 Analytics: make "a change is needed" concrete

The user's core clinical ask is: *identify when a change in curriculum or intervention is required.* Specify it as testable rules, for example:

| Flag | Rule (per program, current phase) |
|---|---|
| Mastered | Mastery rule met (D8) |
| No progress | ≥ 6 sessions in phase and split-middle (or OLS) slope within ±2 pts/week, mean below criterion |
| Regression | Last 3 sessions all below the phase's lower quartile, or slope ≤ −5 pts/week |
| Variable | Coefficient of variation > 30% over the last 6 sessions |
| Stale | No data in 7 days for an active program |

The demo seed must contain one clear example of each. The current answer asks for "an emphasis on different change points", so seed at least one program with three phases.

Graphing convention: **data paths must not connect across a phase line.** The mockup line graph draws through the phase markers.

## 5. Defects inside the specs

- `testing-strategy.md`, `calculatePercentCorrect`: one test expects prompted *in* the denominator (2/4 = 50) and the next expects it *excluded* (1/1 = 100). An implementation can't pass both. (Resolve via D9.)
- `05-rbt-mobile-interface.md` trial screen: "Trial 8 of 10 · 80% · 6 Correct, 1 Prompted, 0 Inc." The 80% matches neither 6/7 nor 6/8, and the bar mixes progress with accuracy. Show the two numbers separately.
- `04-data-visualization.md`: the legend says the current phase is at 85% with criterion 80% × 3 ✓, yet the status reads "On track for mastery". If the criterion is met, the status is *Mastered*.
- `trial-recording.yaml` `on_error: queue_offline` and `.context.md` "try the API, queue on failure" are **online-first**, which contradicts ADR-001's "all writes go local first". Local-first must be the only path.
- `DELIVERABLES-SUMMARY.md` points at `./clarifying-questions.md` and `./phase1-mvp-questions.md`, but the files are `02_…` and `03_…`.
- `README.md` lists `docs/user-guides/`, which doesn't exist.
- `RBT-011`: the "Discard Changes" button actually moves data to drafts. Labels on destructive-sounding actions must say what they do.
- `RBT-004`: "Reset counter" is a destructive control on the busiest screen. Remove it; void-last covers corrections.
- `DEMO-001`: "potential customer" is a sales persona, but the system is for one school. The real Demo persona is *new staff in training* (the turnover requirement).

**Broken links:** 35 relative links in 6 files point to files that don't exist (ADRs 002–004, 8 screen-state YAMLs, 4 persona story files, `technical-spec`, `security-spec`, `api/`, `user-guides/`, `data-flows`, `deployment`). `user-stories.md` also has 32 placeholder `[...](#)` "UI Reference" links. Either create the targets or remove the links. Dangling references mislead an agent into thinking a spec exists.

## 6. Requirements gaps worth adding

- **Inter-observer agreement (IOA):** a standard ABA practice for data reliability. A second observer records the same session and the system computes agreement. It also gives a legitimate reason for two devices on one student (a second, read-only "IOA" role in the lock model).
- **Session-level context:** setting (school/home), who was present, and whether the session was cancelled and why. These are needed later for insurance reports and for explaining outliers.
- **Behavior definitions:** operational definitions for behavior-reduction targets (what counts as one instance of "aggression"), shown to the RBT on the collection screen.
- **Time zones and clock skew:** device clocks drift. Record both `device_time` and server receipt time, and cap acceptable skew.
- **Accessibility of the collection screen:** one-handed use, glove/thumb reach, and screen-reader announcements are partly specified. Add *no colour-only encoding* (✓ ✗ ◐ ○ already help) and a large-text mode.
- **Data export / continuity of care:** listed for discharge. Specify the format (CSV per program plus PDF graphs) even if delivery is Phase 4.
- **Pilot exit criteria** are defined, but measurement is not. Say which table or event each metric is computed from (e.g. "<5% entry errors" = voids + corrections ÷ observations).
